## Appendix A — Feature Inventory (evidence linkage)

Purpose: a pruning-oriented ledger of every substantive feature/engine, what math it runs, which field signals feed it, and — decisive for keeping it — **what actually consumes its output**. Consumer columns were verified by grepping the pinned source revision (`git grep … HEAD -- server/src web/src`), not by reading intent from comments. Evidence status is one of:

- **measured-and-active** — output is consumed by at least one live surface (alarm, HA sensor, UI card, TUI screen, or another engine) and the math has operated on real field data.
- **data-gated (…)** — wired and correct, but a stated gate holds the output at `null`/inactive until the field record satisfies it; the parenthetical names what unlocks it.
- **advisory-dormant** — deliberately advisory or deliberately not wired (documented posture, not an accident).
- **weak-linkage candidate** — no consumer beyond its own ad-hoc endpoint, or math that has never received field validation; one-line justification given. These are the removal-review set collected at the end.

Diagnostic endpoints with a documented validation role (e.g. the forecast backtest) are not flagged merely for lacking an automated consumer; endpoint-only engines with no validation role are.

### A.13 Engine index

An **engine** is a distinct computational unit that implements its own model, estimator, algorithm, planner, controller, detector or alarm evaluation, and whose output is consumed by an alarm, a plan, a device write, a Home Assistant entity, an API field or a UI card. One algorithm counts once, however many reports call it and however many windows, horizons or outputs it serves; the training and inference of one model are one engine. Gates and filters whose only output passes or blocks another engine's result, guards, clamps, integrators and anything whose only output modifies another engine's result are not engines, and neither is plumbing (routing, persistence, formatting, caching, configuration parsing, MQTT discovery, transport, alert delivery, the TUI and the web UI). A gate that also publishes a state of its own, which a consumer reads, is counted as a borderline row: row 29 (the readiness state and its blockers, on a Home Assistant entity, the status endpoint and the card), row 53 (the per-family silence and demotion flags, published on `/api/alert-telemetry`) and row 58 (held spans and the held-row table, read by the night ledger and every samples reader). A rule ladder over another engine's output belongs to that engine: the runway alarm priority and the lighting posture are counted in row 37, the curtailment alert in row 20. A ladder over a direct measurement, such as the SoC bands, is an alarm evaluation and counts. The same statistical method applied to a different signal and baseline, with its own consumer, counts as a separate engine. An evaluation harness with no model of its own is not counted: the forecast backtest stays the validation instrument named under the removal review at the end of this appendix.

**Status** is one of: **live** (computed by default and reaching an alarm, a plan, a dashboard card or another engine); **live-opt-in** (its only consumer besides the HTTP API is a channel that is off by default: `BROADCAST_ENABLED`, `NOTIFY_CHANNEL` or `MQTT_DISCOVERY_ENABLED`, which carries every Home Assistant entity); **advisory-only** (published only on the HTTP API, or as advice the add-on never acts on); **shadow** (computed, published and scored, never acting; no row carries it today, and the shadow-only winter mid-day cycle is described inside row 27; the online-trained pack-risk file the code calls its shadow is the model row 25 serves, so it is advisory-only, not shadow); **write-capable-gated** (can write to a device behind mode gates, none of which is open under the shipped defaults). **Tier** is **core**, or **borderline** where a stricter reading of the definition could fold or drop the row. **Code** names the file and an identifier the file declares only while the engine exists; `scripts/check-doc-claims.mjs` fails a row whose file no longer declares that identifier in code: a function, class, const, let, var, interface, type, enum or namespace declaration of exactly that name, outside every comment and string, so a rename that leaves the old name in comments fails, and so does a removal that leaves a caller behind. Rows 45 and 49 anchor to identifiers local to the function that hosts them (`imbPts` inside `computeForecastAlerts`, `FADE_PEER_Z_FLOOR_PCT_PER_YEAR` inside `computeDegradation`), so a rename fails the check while the engine still exists and the row is then re-anchored.

**62 engines**: **27** in the analytics worker, **35** on the main thread. Read strictly (core rows only, without the advisory-only and shadow rows), the index holds **44**. Of those, 39 are live under the shipped defaults; the other 5 wait on a channel or a write mode that is off by default (the Status column names them). The project's prose states only a floor below the strict reading: more than 40 engines.
