## 8. Alerts, Anomaly Detection, Incidents & Learning Loop

This is the complete reference for the ecoflow-panel alerting subsystem: how conditions become alerts, how learned/anomaly alerts are derived, how the monitor turns the per-tick alert list into notifications, incidents, and telemetry, and how operator feedback feeds a learning loop. Everything below is drawn from the actual source in `server/src/` — real function names, constants, thresholds, endpoint paths, and env keys.

The architecture is a pipeline:

```
                            ┌── computeAlerts()        (threshold, alerts.ts)
                            ├── computeLearnedAlerts() (peer-comparison)
                            ├── computeBaselineAlerts()(self-baseline)      ─┐  analytics.ts
                            ├── computeForecastAlerts()(degradation/runtime) │
snapshot.devices ─► evaluateInner() (alertMonitor.ts) ├── forecastDayAlerts()   (solar/load)          ─┘
                            ├── outageAlerts()         (data-gap events)
                            ├── broadcastHealthAlert() (audible self-alert)
                            └── rateFloorAlerts()      (msg-rate collapse)
                                       │
                                       ├─► store.setAlerts()   → snapshot.alerts → /api/snapshot, WS
                                       ├─► buildIncidents()     → /api/incidents
                                       ├─► rising/falling edges → notify.ts (HA drawer + mobile_app push) + digest
                                       ├─► telemetry rollups     → /api/alert-telemetry (drives auto-silence)
                                       ├─► featureSnapshot capture → learning loop
                                       └─► cleared log            → /api/alerts/history
```

Two independent identity concepts run throughout and must not be confused:

- **`alert.id`** — the stable per-subject key, e.g. `soc-low-<SN>-<packNum>`, `dpu-err-<SN>`, `peer-temp-<SN>-<pack>`. It is the notification dedup key and the cleared-history key.
- **`familyOf(alert.id)`** (`alertOutcomes.ts`) — the rollup key that strips device serials and trailing pack numbers, e.g. `soc-low`, `cell-imbalance`, `pack-hot`. Auto-silencing and outcome precision are keyed by **family** so a condition spread across 5 packs aggregates as one statistical unit.

### 1. The `Alert` type and priority taxonomy

#### The `Alert` shape (`alerts.ts`)

```ts
interface Alert {
  id: string;
  severity: 'critical' | 'warning' | 'info';
  category: 'Battery' | 'Solar' | 'Thermal' | 'SHP2' | 'Grid' | 'Connectivity';
  device: string;
  title: string;
  detail: string;
  source?: 'threshold' | 'learned';       // default 'threshold'; 'learned' = anomaly/forecast engine
  priority?: 'critical' | 'high' | 'medium' | 'low';  // explicit ISA tier (wins over the heuristic)
  coreNum?: number | null;                // subject identity: Core (DPU) number — topology.coreNumber: from the
                                          //   Core's name, else its panel slot when it has no name of its own (v1.191.0)
  packNum?: number | null;                // subject identity: pack number
  facts?: AlertFact[];                    // { label, value } statistical breakdown
  fault?: string;                         // v1.64.0 sub-identity: WHICH fault, when one id spans many
  sourceSn?: string;                      // v1.78.0 serial whose telemetry proves the condition (falling-edge evidence gate)
  sourcePackSn?: string;                  // v1.102.0 BMS-reported pack serial on pack-scoped alerts
  annunciate?: boolean;                   // false = VISIBLE but never chime/push/raise-condition
  audible?: boolean;                      // v1.187.0 false = card + push, never raises or voices the broadcast condition
  mutedBy?: VdiffCritMuteReason;          // v1.187.0 the bounded cell-spread mute holding a vdiff-crit this tick ('balancing' | 'end-of-charge' | 'charging' | v1.195.0 'low-charge')
  muteReason?: string;                    // v1.187.0 why annunciate is false, in words (diagnostic only)
  shelvedUntilMs?: number;                // v1.197.0 a maintenance window holds it: the window's end (read by the all-clear gate)
}
```

Three fields carry most of the subtlety:

- **`fault`** (v1.64.0) — a short, **stable**, machine-readable discriminator for
  *which* fault this is, set only where the `id` is deliberately reused across
  materially different faults. `dpu-err-<sn>` is emitted for **every** value of
  `sysErrCode` (the id is held constant so a standing fault does not re-raise on
  upgrade), and `shp2-src-err-<slot>` likewise — with a title that never varies at
  all. Both set `fault: err<code>`. `redReplayGate.alertFingerprint` folds
  `id + title + fault` into the identity the post-restart red replay gate compares,
  so a code change is a *different fault* and always announces. ★ It must never
  carry a live measurement (watts, mV, percent, temperature) or a timestamp: a
  value that drifts every tick makes every fingerprint unique and silently turns
  that gate into a no-op. Omit it when the id already names exactly one fault.
- **`annunciate: false`** — the annunciation gate (v0.16.4). The condition still renders in `snapshot.alerts` (never hide an active alarm), but it must never produce an audible broadcast, a push, or raise the broadcast condition level. Used for expected steady states (a designated bench spare offline). Both annunciation channels honour it: `broadcast.conditionFromAlerts` (audible) and the monitor's rising-edge router (push/digest).
- **`priority`** — explicit ISA-18.2 tier. When present, `priorityOf()` reads it FIRST and skips the severity+source heuristic. Lets a *real* measured threshold crossing reach ISA Medium without faking `source='learned'` (which would misroute it to the Predictive page).

#### ISA-18.2 / IEC 62682 priority derivation (`alertPriority.ts`)

`priorityOf(alert)` is the single source of truth:

```
if alert.priority present          → use it verbatim
else if severity === 'critical'    → 'critical'  (P1)
else if severity === 'warning'     → source === 'learned' ? 'medium' (P3) : 'high' (P2)
else                               → 'low'        (P4)
```

| Priority | ISA | rank | colorToken | rung | klaxon asset | Meaning |
|----------|-----|------|-----------|------|--------------|---------|
| critical | P1  | 0 | bad  | `critical` | `red-alert.wav`               | Immediate action to protect people/battery/plant |
| high     | P2  | 1 | high | `high`     | `powerplant-red-alert.wav`    | Protective hardware limit crossed; prompt action |
| medium   | P3  | 2 | warn | `medium`   | `yellow-alert.wav`            | Learned/statistical anomaly; investigate |
| low      | P4  | 3 | info | `low`      | `powerplant-yellow-alert.wav` | Advisory / situational awareness |
| —        | —   | — | ok   | `clear`    | `all-clear.wav`               | Recovery — not a priority; see `AlarmRung` below |

The High-vs-Medium split on `source` is itself ISA logic: a deterministic threshold breach is more certain and more actionable than a learned deviation. `notifyBracketPriority(alert, effectiveSeverity)` computes the `[Medium]`-style title bracket, honouring the explicit priority UNLESS auto-tune demoted the severity for this send (then the demoted severity drives the bracket → `[Low]`). The web app mirrors this file at `web/src/alertPriority.ts` and the two must stay in lockstep.

**`AlarmRung` (v1.59.0) — the audible vocabulary.** `type AlarmRung = AlarmPriority | 'clear'`, ordered by `ALARM_RUNG_ORDER`. Each of the four priorities now carries its **own** tone, plus a fifth rung for recovery. Before v1.59.0 the audible path collapsed to three levels (`red`/`yellow`/`green`) via `klaxonLevelForPriority()`, so P1 and P2 were audibly identical, as were P3 and P4 — the operator could not tell a critical from a high by ear, which matters most on the chime-only fallback where the tone is the entire message.

`clear` is deliberately **NOT** a member of `AlarmPriority`, for three independent reasons:

1. `ALARM_PRIORITY_ORDER` drives **retained** MQTT discovery (`mqttDiscovery.ts`). A fifth member mints `switch.ecoflow_alarms_clear_p5` permanently, and there is no reaper for retained discovery topics.
2. `ALARM_PRIORITY_META` requires an `isa` string and the builder calls `.toLowerCase()` on it; a recovery has no ISA tier.
3. `priorityOf()` structurally cannot return it — nothing classifies an alert as "cleared"; clearing is the *absence* of raised alerts.

`klaxonLevelForPriority()` survives, but ONLY for legacy bookkeeping (`lastLevel`, cooldown/status reporting). It no longer selects a tone — every `resolveChime()` / `renderAnnouncement()` call site takes the rung. Do not reintroduce it on the audio path.

### 2. Threshold alerts — `computeAlerts()` (`alerts.ts`)

**WHAT.** The static-rule engine and the single source of truth for `snapshot.alerts`. Given the device map (plus optional connectivity and grid context) it returns a sorted `Alert[]`. The web UI renders this; the monitor uses the same output to decide what to push.

**Signature:** `computeAlerts(devices, connectivity?, grid?, poolGrid?)`. `poolGrid?: (panelSn) => verdict` (v1.185.0) is passed only on a multi-panel plant; each pool's reserve alarms then read their own panel's verdict (`livePoolGridBackstop`) instead of the plant `grid`.

- `grid?: { present?, backstopping?, reason? }` — when the grid backstops the home, at/near-reserve conditions merely transfer to mains and are downgraded critical→info (still visible, no chime). Omitted ⇒ treated as off-grid (safe default).
- `connectivity?: ConnectivityContext` — carries last `/device/list` attempt/success timestamps, per-device MQTT last-seen/count, and several debounce-onset maps read from the snapshot store (`backupPoolUnknownSinceMs`, `dpuErrOnsetBySn`, `shp2SrcErrOnsetBySlot`).

#### 2.1 Constants and temperature bands

| Band | infoF | warnF | critF |
|------|-------|-------|-------|
| `CELL_TEMP` | 104 | 113 | 131 |
| `MOS_TEMP` | 104 | 131 | 149 |
| `BOARD_TEMP` | 113 | 140 | 158 |
| `SHUNT_TEMP` | 113 | 140 | — |
| `MPPT_TEMP` | 131 | 149 | 167 |
| `CELL_TEMP_COLD_F` | — | — | ≤ 41 °F fires a cold-charge-derate warning |

`classifyTemp()` converts °C→°F (`cToF = c*1.8+32`) and returns the highest band crossed. `tempAlert()` builds the alert with verb (`overheating`/`running hot`/`getting warm`).

#### 2.2 Alerts emitted (id → condition → severity)

**System / connectivity:**

- `cloud-session-stale` (warning, Connectivity) — no successful `/device/list` in `CLOUD_SESSION_STALE_MS`; per-device online flags are last-known, not current.
- `host-power-undervoltage` (warning, Connectivity) — the under-voltage `binary_sensor` named by `HOST_POWER_ENTITY` (on a Raspberry Pi host, Home Assistant's Raspberry Pi Power Supply Checker) reads on; early warning that the host running the monitor is browning out. The detail names the host and the entity, not a particular board (safety chapter, `hostPower.ts`).
- `host-temp-warn` / `host-temp-crit` (warning / critical, Connectivity) — the alarm host's SoC temperature past `HOST_TEMP_WARN_C` / `HOST_TEMP_CRIT_C`, with rise/clear hysteresis (§13.0).
- `host-pressure-warn` / `host-pressure-crit` (warning / critical, Connectivity) — one rolled host-resource-pressure alert; it rises as critical only once crit pressure has stood its dwell (`hostPressureCritSustained`, §13.0b), and since v1.187.20 the warning is audible only after the warning dwell (§13.0b).
- `tts-render-degraded` (warning, Connectivity) — ≥ 2 consecutive failed fresh TTS renders; chimes still deliver, without speech (§10, 4.7).
- `shp2-multi-panel` (critical, SHP2, explicit `priority: 'critical'`) — two or more smart panels with none pinned as the house panel, or the pinned house panel missing from the device list. Supervised reserve and Charge-Now writes are blocked while it stands. In `isNeverMutedAlert` (§2, *Two panels (v1.185.0)*).
- `grid-offgrid` (info, Grid) — off-grid. Decision uses `grid.present` when supplied (the same resolver behind `binary_sensor.off_grid`); falls back to `acIn < 5` W over SHP2-bound cores only. Wall-charging spares never register as grid.
- `offline-<SN>` / `offline-spare-<SN>` (warning for Core/Panel, info otherwise; spare=info+`annunciate:false`) — device offline per `/device/list`. Enriched with last-data age/source, MQTT count, and a cause-matched hint (**v1.187.1:** only for a measured gap — a device with no data since the add-on started is said to have "not reported since the add-on started", with how long EcoFlow has reported it offline when this session saw it go offline (`onlineChangedAtMs`), or else that it has been listed offline since the add-on's first device list and for how long (`ConnectivityContext.perDevice.firstListedAtMs`, from `SnapshotStore.firstListedAt`), and that the cause is not known; no ">30 min", no cloud-session cause, no power-cycle advice. A device with REST data but no MQTT this session states its last data instead of "no telemetry". Whether the device has reported is decided from data — a last source or MQTT time in the store, or the device's `lastTelemetryAtMs` / `lastQuotaAtMs` — never from `lastUpdated`, which a bare MQTT `/status` online/offline flip also bumps (`setDeviceOnline`); a device whose only traffic this session was such a flip is still "not reported since the add-on started"); when `ECOFLOW_DEVICE_REACHABILITY` is configured, `classifyDeviceLink()` adds a `cloud_wedge` vs `real_outage` fact and hint. **v1.187.10:** the listing time is per process, so after every restart the hint said "listed offline since the add-on's first device list (5 h ago); how long before that … is not known here" of peripherals the repair card had on record as offline for 89–104 days. The alert monitor now keeps a restart-persistent "first seen listed offline" stamp every evaluation (`repairIssues.syncCloudOfflineFirstSeen`, the `cloud-offline-<SN>` entries of `repair-first-seen.json`): set when a device that is not a bench spare is first seen listed offline, cleared only when it is listed ONLINE (an MQTT `/status` online flip counts), and persisted on either change; absence from a list, or a `/api/repair-issues` fetch on a map without the device, clears nothing. When the stamp predates this process's first listing (`ConnectivityContext.perDevice.offlineSinceMs`), the hint reads "listed it offline since at least `<age>` ago (first seen offline before the add-on's last restart, and not seen online since)"; a stamp taken in this process leaves the v1.187.1 wording. The repair card's `firstSeenAt` for the same device is the same stamp. Explicit priority: Panel=high (alarm data source), Core=medium, peripheral=low, spare=low. **v1.187.10 — onset hold** (`cloudOfflineOnsetHeld`): a home Core listed offline while its own MQTT data still arrives (a data message within `CLOUD_OFFLINE_MQTT_LIVE_MS`, 90 s) is on screen at once but `annunciate:false` (`MUTE_REASON_CLOUD_OFFLINE_MQTT_LIVE`, and an `Onset hold` fact) — not spoken, not pushed, not counted toward the condition — for `CLOUD_OFFLINE_ONSET_HOLD_MS` (3 min) from the transition (`onlineChangedAtMs`). It is judged on every evaluation: the moment no data message has landed for 90 s, or the hold runs out, it annunciates as before, and its push dwell has already run (it counts from the first sighting). Never held: a device with no transition seen in this process (offline at the first device list), no MQTT data this session, a peripheral, a bench spare, or the panel — its MQTT messages stamp `lastMqttAt` but are never translated into its projection (only Core quotas are), and its REST quota is fetched only for devices listed online, so while it is listed offline its backup pool, reserve, grid status and `lastQuotaAtMs` are frozen and arriving panel data is not evidence the alarm inputs are live. 2026-10-03 19:31, right after a WAN drop, the device list flagged the panel and every Core offline in one poll; the condition went yellow in the same second, was spoken for 92 s and three Medium pushes went out, and every flag cleared within about 2 minutes. Residual: a device whose data stops at the same moment as the flag is held until its last message is 90 s old.
- `stale-<SN>` / `stale-spare-<SN>` (warning; spare=info) — online per EcoFlow but no fresh telemetry for > `STALE_MS`.

**Per-DPU (Core), for online DPUs:**

- `dpu-err-<SN>` (critical, Battery) — `sysErrCode != 0`, **debounced** by `DPU_ERR_DEBOUNCE_MS`: suppressed until the SAME code has stood 3 min (cloud-reconnect blips 20–160 s are dropped). No onset context ⇒ fires immediately (never silently loses a real fault).
- `dpu-pvh-err-<SN>` / `dpu-pvl-err-<SN>` (warning, Solar) — HV/LV MPPT error code AND the string is actually producing per `mpptProducing(watts, amps)` (`server/src/mppt.ts` since v1.174.0; needs BOTH watts > 20 W and, if reported, amps > 0.3 A) AND, since **v1.174.0**, the SAME code has stood for `MPPT_ERR_DEBOUNCE_MS` (3 min, shared with the inverter-error and SHP2-source-error windows). The producing test rejects sunset/dusk standby codes that are identical across independent cores; the debounce rejects the SUNRISE case the producing test cannot see, where the same standby code rides a ramping string that is genuinely producing (2026-09-22: 407 W / 301 V / 1.38 A, ~60 s, twice). The window is measured by `SnapshotStore.trackMpptErrOnsets` (keyed `<sn>:hv` / `<sn>:lv`), whose clock advances only while the code is non-zero AND the string is producing — so a code standing overnight on a dark string banks no time, and no onset context at all (older callers, unit tests) fires immediately.
- `mppt-hv-temp-<SN>-<severity>` / `mppt-lv-temp-<SN>-<severity>` — `MPPT_TEMP` band (`tempAlert` appends the band's severity to the id). Channel slug precedes SN so `familyOf` yields per-channel families.
- `ems-volt-<SN>` (info, Battery, `priority: 'low'`, `audible: false`; **v1.187.3**, a warning until then) — "Pack voltage swing outside EMS band": `batVol` outside EcoFlow's `emsParaVolMin/Max` parallel band. The band is relative, not a limit: 2.3-3.0 V wide around a reference voltage the Core reports in the same ~5-minute backend block as `batVol`, within about 40 mV of `batVol` at rest, and found anywhere from 81.6 to 112.4 V across the cleared ledger. `batVol` leaves it on a fast current change (night grid-charge onset, an evening load step) or at the top of charge: 33 home-Core episodes from 2026-08-25 to 10-01 had `batVol` 102.3-109.3 V and a highest cell of at most 3.512 V. As a warning it took ISA High, raised the yellow, was spoken and pushed — the one audible alarm of a top of charge on 2026-10-01 (108.9 V, 0.45 V below a 109.4-112.4 V band, highest cell 3.494 V). As info it stays on the card, below the push minimum, and is never counted toward or voiced in the broadcast condition; the detail says whether `batVol` is below or above the band and that the band is not a voltage limit. A real overvoltage is `cell-ovp-*` (critical at 3.600 V, never muted) and an inverter/BMS fault `dpu-err-*`; neither reads the band. The band is recorded (`ems_para_vol_min_mv` / `ems_para_vol_max_mv`, §1, 4.3), and its cleared rows keep the warning eviction tier (`CLEARED_INFO_KEPT_AS_WARNING_PREFIXES`).
- `dpu-imbalance-<SN>` (warning) — SoC spread across the DPU's packs ≥ `PACK_IMBALANCE_WARN_PCT` (15%).

**Per-pack (each DPU pack):**

- `soh-crit-<SN>-<pk>` (critical) / `soh-warn-<SN>-<pk>` (warning) — `actSoh ?? soh` below 75 / 85%.
- `vdiff-crit-<SN>-<pk>` (critical) / `vdiff-warn-<SN>-<pk>` (warning) — cell spread. **v1.187.14:** a warn-band spread pushes only below the plateau (`plateauQuietWarnSpread`, < `VOL_DIFF_PLATEAU_SOC_PCT` 85%); from 85% it is visible without a push (the 95% line still bounds the critical's graces). **v1.187.12:** `vdiff-warn` carries `audible: false` — its card and push stand, it never raises the spoken condition; `vdiff-crit` is unchanged. **v1.187.21:** the same pack's peer cell-spread outlier at warning carries `audible: false` too (§3.1), so a warning-level cell spread reaches no speaker by either report; `vdiff-crit` is the audible signal. **Rise-side hysteresis** (F28): warning fires only at ≥ `VOL_DIFF_WARN_RISE_MV` (24 mV), then HOLDS while still ≥ `VOL_DIFF_WARN_MV` (20 mV); held state is keyed `${sn}-${pk}` and pruned each cycle for any pack that produced no reading. Critical at ≥ `critMv` where `critMv` = 90 mV on the plateau (`packSoc ≥ 85%`) else 50 mV. Three `annunciate:false` demotions keep benign excursions visible-but-silent: (a) `balanceState != 0` (BMS actively balancing; on a critical, bounded by `vdiffCritMute` below), (b) a plateau-benign excursion (would be crit off-plateau but under the relaxed plateau ceiling, BMS idle), (c) **v1.45.0, widened v1.187.14** — any warn-band spread on a pack at ≥ `VOL_DIFF_PLATEAU_SOC_PCT` (85%; `plateauQuietWarnSpread`; ≥ `VOL_DIFF_PLATEAU_QUIET_SOC_PCT` 95% until v1.187.14): at top of charge the LFP curve transiently widens warn-band spread fleet-wide (observed: 14 of 15 packs within two hours of a full top-up, all self-clearing), so those stay visible without pushing. Silence is bounded — for (b) and (c), SoC dropping below the respective plateau line re-arms standard annunciation; for (a) on a critical, the session bounds below. The critical and the plateau lines (`VOL_DIFF_CRIT_MV`, `VOL_DIFF_PLATEAU_*`, `vdiffCritMvFor`, `plateauQuietWarnSpread`) live in `cellSpread.ts` (shared with the peer engine from v1.187.0 until v1.187.21, which retired its only reader there, `topOfChargeQuietSpread`). **v1.187.0 — the critical's mute is `vdiffCritMute`'s alone**, over per-pack state from `advanceVdiffKnee` (keyed `${sn}-${pk}`, bound to the pack serial): a spread ≥ `VOL_DIFF_KNEE_HARD_MV` (150 mV) annunciates at any SoC, balancing or not; on the plateau, a spread first at the critical line `VDIFF_KNEE_MAX_MUTE_MS` (20 min) ago annunciates even while balancing ("First reached the critical line N minutes ago."); otherwise `balancing` mutes (`mutedBy: 'balancing'`), for at most `VDIFF_KNEE_MAX_MUTE_MS` from the session's first crossing on the plateau and (v1.195.0) from the off-plateau session's below it (see **Below the plateau** at the end of this entry). At ≥ 95% SoC two narrower graces follow, each fed by evidence recorded only while the spread is ≥ `VOL_DIFF_WARN_MV`: (1) **end-of-charge** (`mutedBy: 'end-of-charge'`, detail "End-of-charge cell spread, relaxing.") for `VDIFF_KNEE_RELAX_MS` (5 min) after the last BALANCING tick — the observed benign mechanism, since every benign reading ≥ 90 mV in the recorder had balancing on; (2) **charging** (`mutedBy: 'charging'`, detail "Top-of-charge cell spread while charging.") while stream-delivered charge input > `VDIFF_KNEE_CHARGE_W` was seen within `VDIFF_KNEE_RELAX_MS` AND the session's first crossing (below) was less than `VDIFF_KNEE_RELAX_MS` ago — measured from the first crossing, never the last charge tick, so a steady trickle cannot refresh its own mute (charge-only benign peaks: 84 and 77 mV; the one charge-only reading ≥ 90 mV in history was a fault). **Both graces are bounded by the SESSION (v1.187.0 log review).** `graceFromMs` is the first critical-line crossing seen on the plateau, at ≥ `VOL_DIFF_PLATEAU_SOC_PCT` (85%) SoC (**v1.187.2** — until then the first seen at ≥ 95%, from the running episode's own first crossing when it began lower on the plateau); it is not reset when the spread falls under 50 mV, and is carried across reading gaps like the critical-line clock. It is cleared by a reading below 85% (until v1.187.2 below 95%; a missing SoC does not clear it) or once the pack has **rested** on the plateau: an unbroken `VDIFF_KNEE_MAX_MUTE_MS` of readings under 50 mV (`quietSinceMs`; started only at ≥ 85% (v1.187.2; ≥ 95% until then), broken by any reading at or above 50 mV — one with no SoC included — not started by a reading with no SoC, and not carried across a reading gap — a rest must be seen). The charging grace lasts at most `VDIFF_KNEE_RELAX_MS` and the end-of-charge grace at most `VDIFF_KNEE_MAX_MUTE_MS` from it, and while it runs the **balancing mute** too lasts at most `VDIFF_KNEE_MAX_MUTE_MS` from it, at any SoC the session stands at ("First reached the critical line at this top of charge N minutes ago." at ≥ 95%, "First reached the critical line above 85% charge N minutes ago." below). The graces themselves apply only at ≥ 95%, and a session begun lower on the plateau bounds them from that first crossing (fail loud: a crossing at 90%, no rest, then 95 mV at 97% on a 600 W charge annunciates at once). **v1.187.2** — until then no session ran between 85% and 95%, so the balancing mute there was bounded by the critical-line clock alone, which (v1.187.1, log review) survives readings under the line shorter than `VDIFF_KNEE_RELAX_MS` (below) but ends after a longer run: a balancing spread at 95 / 45 / 45 mV on a ~180 s cadence, 95 / 45 mV with one reading missed, or 95 / 70 / 70 mV restarted the bound on every crossing and was never announced; it now annunciates on the first critical tick at or past `VDIFF_KNEE_MAX_MUTE_MS` from its first crossing (at most one reading later), in-process and across a restart. Measured from the current crossing instead, each dip under 50 mV restarted both: a spread that follows the charge current on isolated readings (95 / 45 mV every ~180 s at 97% on a 600 W charge) was held as "charging" on every crossing for a whole afternoon, and a 100 mV reading between balancing 45 mV readings as "end-of-charge"; both now annunciate on the first critical reading past the bound, and so does a spread balancing on alternate readings (95 mV balancing / 45 mV), which the episode-bound balancing mute held for hours. A second knee in the same session without a rest gets no second grace and annunciates (fail loud); a pack that rests on the plateau for 20 minutes, or discharges below 85% and charges back, starts a new session (v1.187.2; at the top of charge and below 95% until then) — a benign pack relaxes to 3-30 mV within minutes, while a spread that follows the charge current is never under 50 mV for 20 minutes. Charge input is `vdiffKneeChargeW`: `DpuPack.streamInputW`, the pack's `inputWatts` exactly as the MQTT stream delivered it, at most `VDIFF_KNEE_STREAM_FRESH_MS` old — never the REST value (the poll replays the last non-zero reading) and never `liveFlow` (which falls back per field to the polled value); absent or stale ⇒ no charge evidence ⇒ the critical keeps only its balancing grace. A spread still at the line when a grace lapses annunciates ("Did not relax at the top of charge."). The BMS reports cell voltages every ~180 s, so the window always holds a reading taken ≥ 2 min after balancing stopped; benign top-of-charge spreads ≥ 90 mV were back under it within 2.7 min, slow-relaxing ones (110-138 mV, 3-9% in 3 min) annunciate. The critical-line clock ends when the pack leaves the plateau, or once the spread has stayed under the plateau line for an unbroken `VDIFF_KNEE_RELAX_MS` (one sub-line reading does not end it). **v1.187.1 (log review)** — that includes readings under 50 mV, which used to end it at once: between 85% and 95% no session ran until v1.187.2, so this clock was the balancing mute's only bound there, and a balancing spread alternating 95 / 45 mV every ~180 s restarted it on every low reading and was held silent with no limit (and the persisted session held its latest crossing, or none, so a restart did not catch it either). It now annunciates on the first critical reading at or past `VDIFF_KNEE_MAX_MUTE_MS` from its first crossing ("First reached the critical line N minutes ago."), and the file carries that first crossing across a restart. A spread that stays under the line for 5 minutes between crossings starts a new episode each time, as before; since v1.187.2 the session still bounds it. A clock seeded from a persisted onset (`vdiffKneeSeed`: never seen in a process) still ends on a reading under 50 mV, as in v1.187.0 — the onset may be a day old, and kept for five more minutes it made the next day's benign knee annunciate. **v1.187.2** — on ANY reading under 50 mV until a reading at the critical line confirms it (`VdiffKneeState.critSeeded`: set by `vdiffKneeSeed`, cleared by a reading at or above `vdiffCritMvFor(packSoc)` and whenever `critSinceMs` is cleared), where v1.187.1 applied it only to the first reading after the restart, so a first reading at 50-89 mV kept a day-old onset through the readings under 50 mV after it. The mark is written to the knee-session file with the clock (`critSeeded: true`, present only while set; a non-boolean value makes the entry malformed) and restored with it (a mark with no clock is dropped): without it the restore read the clock as one a process had seen, and a second restart restored the day-old onset unmarked. For v1.187.1, the recorded days with top-of-charge spreads (2026-07-23, 07-28, 09-18, 09-25 and 09-29, every pack, replayed through `computeAlerts`) gave the same critical ticks and the same annunciations as before. On a reading gap the activity evidence is dropped (re-earned from fresh readings) but the clocks (`critSinceMs`, `graceFromMs`) are carried, bound to the pack serial, for `VDIFF_KNEE_GAP_CARRY_MS` from the last reading, so offline blips cannot restart the duration bound or re-grant a grace. **Across a restart (v1.187.1)** the clocks are persisted per pack: `vdiff-knee-state.json` beside the database (`VDIFF_KNEE_STATE_PATH` overrides) holds, for each `${sn}-${pk}` holding a clock, the pack serial, `critSinceMs`, `graceFromMs`, the rest (`quietSinceMs`), the last reading time and (v1.187.2) the seed mark (`critSeeded`), floored to `VDIFF_KNEE_SEEN_PERSIST_MS` (5 min). The monitor restores it at start-up, before its first evaluation (`restoreVdiffKneeSessions`), and writes it after each `computeAlerts` only when a persisted value changed (`persistVdiffKneeSessions`): a serial, a clock or the rest, an entry gained or lost, or the last reading entering a new 5-minute grain — never on a tick that changed nothing. The grain turns on the same tick for every pack seen, so the last reading costs one write per 5 minutes however many packs hold a session. The restore applies the in-process gap rule: an entry is carried while the pack's last reading is at most `VDIFF_KNEE_GAP_CARRY_MS` old — the outage, never the onset's age — reading the file's last-reading time as the latest the true one can have been (file value + 5 min − 1 ms, capped at the restart; that bound floors back to the file value, so restarts that see no reading cannot walk it forward), and dropped after it. As across any reading gap, the activity evidence (`lastBalancingMs`, `lastChargeMs`) and the under-the-line run (`belowCritSinceMs`) are neither persisted nor restored: a mute is re-earned from fresh readings. The rest is restored only when the file's last reading is at most `VDIFF_KNEE_SEEN_PERSIST_MS` + `VDIFF_KNEE_RELAX_MS` (10 min) old at the restart — that age bounds the outage from above, and at most three ~180 s BMS readings fall inside it — and starts over at the restart otherwise; a pack unseen on a tick after the restart loses it, as in the process. It is also restored only when it is coherent (`vdiffKneeRestCoherent`, v1.187.1 log review): an unfinished rest inside a running session, begun after the session's first crossing and, while an episode still stands, after that episode's first crossing (the episode outlives the first `VDIFF_KNEE_RELAX_MS` of a rest), and less than `VDIFF_KNEE_MAX_MUTE_MS` before the file's last reading. Anything else — 0, a negative clock, a rest before the session — came from a corrupt file and starts over at the restart: restored, a rest dated far enough back ended a running session on the first reading under 50 mV and granted the next crossing fresh graces. Started over at every restart, the rest after a benign knee kept the restored session up to 20 minutes longer than the process would have, and a second benign knee inside that window (two knees 30 minutes apart, the add-on restarted 12-25 minutes after the first) sounded the red klaxon. After a longer outage the rest must be seen again for 20 minutes, and a second knee inside that window annunciates (fail loud). A spread that follows the charge current breaks its rest on every crossing, before and after a restart (hi / lo / lo with a crossing hidden inside the outage rests at most 15 minutes); only a spread crossing the line on one reading in four or fewer (about every 12 minutes or longer) can have its session ended by a crossing hidden inside a restart's outage — the add-on down for at least one whole ~180 s reading — and its next crossing then earns one more session's graces (a spread with 20 minutes under 50 mV between crossings ends its session in the process alike). A clock ahead of the restart (a clock step) is clamped to it; the restored state stays bound to the pack serial. Restored by the onset's age instead (v1.187.0), a fault that crosses the line on isolated readings came back from a restart on a sub-line reading with no session — its onset held through the resolve dwell for over an hour (95 / 45 mV alternating), or already retired (hi / lo / lo) — and the next crossing opened a new session with up to `VDIFF_KNEE_MAX_MUTE_MS` more silence; it now stays loud. A missing, unreadable or malformed file is ignored with one log line, and a malformed entry is skipped and counted in that line. A pack the file holds no entry for — the file ignored, or the outage longer than the carry — starts from `vdiffKneeSeed`: the persisted onset of its standing `vdiff-crit-<SN>-<pk>` (alertOnset.ts), clamped to now, seeds both clocks — the session clock only from an onset at most `VDIFF_KNEE_GAP_CARRY_MS` old (an onset persisted before a long outage that began inside a knee is not the current session, and seeded it was never ended, so the next day's benign knee had no grace; a critical still standing re-derives the session from the seeded critical-line clock on its first reading at the line and still fails loud) — and the current reading then clears whichever it contradicts. The evidence is never seeded. An onset is at or before the true first crossing, so the bounds can only come due sooner (fail loud): a restart at minute 21 of a balancing-held spread keeps it annunciating ("First reached the critical line 21 minutes ago.") instead of buying up to 20 more minutes of silence, and a restart inside a grace does not re-grant it. A pack with neither an entry nor a standing critical starts fresh. The key is pack SoC, never the max cell alone: a runaway-high cell on a mid-SoC pack stays an immediate critical. **Below the plateau (v1.195.0) — the off-plateau session and the low-charge knee.** The bounds above run only on the plateau and are cleared below it, so below 85%, and whenever the pack's SoC is unknown, the balancing mute had no limit at all: 80 mV at 60% stayed muted for as long as the BMS balanced, a balancing spread alternating 55 / 45 / 45 mV on the ~180 s cadence was never announced, and a pack whose SoC read 84 / 85% on alternate readings restarted its plateau session on every 85% reading. A critical below the plateau or with no SoC now opens an **off-plateau session** (`offFromMs`) on its first reading at or above `VOL_DIFF_CRIT_MV`; an on-plateau reading never opens one. Dips under the line do not end it: only an unbroken `VDIFF_KNEE_MAX_MUTE_MS` of readings under 50 mV, at any SoC (`offQuietSinceMs`, broken by any reading at or above 50 mV), does. `vdiffCritMute` returns no mute below the plateau without a session, or once `VDIFF_KNEE_MAX_MUTE_MS` has passed since its first crossing ("First reached the critical line below 85% charge N minutes ago.", "…with no charge reading…" with no SoC, on a balancing or low-charge reading), so the 84% readings of the 84 / 85% flicker annunciate from 20 minutes. Inside that bound the balancing mute applies as before, and so does a new grace, the **low-charge knee** (`mutedBy: 'low-charge'`, muteReason "low-charge cell spread, at most 20 minutes", detail "Low-charge cell spread."): below about 15% the LFP curve is steep and the cell holding the least charge falls away from the rest and closes back on recharge, so a healthy pack at the bottom of a discharge crosses the instantaneous 50 mV line (2026-08-20: Core 5, cleared in 6.7 minutes; 08-16 about 5 minutes). The critical stays on the card, not pushed and not sounded, the treatment the top-of-charge knee gets, while the reading is the knee (`lowChargeKnee`: the pack's OWN SoC at or below `VOL_DIFF_LOW_KNEE_SOC_PCT` (15%) and less than `VOL_DIFF_LOW_KNEE_PEER_PTS` (10) points below the upper median of its sibling packs' own SoC readings, which needs the pack's own SoC and at least two siblings reporting) and every reading at the line in the session was one (`offKnee`: one that is not — above 15%, with no own SoC, or stranded — forfeits the grace for the session). These get no low-charge grace: a stranded pack, 10 or more points below its siblings (the 07-18 → 08-23 warranty pack read 11% against 58% and 1% against 21-26%; detail "Pack at X% charge against a sibling median of Y%."), and a session that reached the line on any other reading. They page at once while the BMS is idle. While it reports balancing, `vdiffCritMute` checks the balancing mute first and holds them (`mutedBy: 'balancing'`, the stranded note on the card throughout); they speak `VDIFF_KNEE_MAX_MUTE_MS` after the session's first crossing, like any balancing critical below 85%. 150 mV or more pages at once, balancing or not. The session is carried across a reading gap under `VDIFF_KNEE_GAP_CARRY_MS` like the plateau clocks (its rest is not: a rest must be seen), is seeded by `vdiffKneeSeed` from a standing critical's onset under the same age cap (a seed never earns the low-charge grace), and is persisted in `vdiff-knee-state.json` as `offFromMs`, `offQuietSinceMs` and `offKnee: true`, each written only while set (an entry with no off-plateau session keeps its earlier shape; an entry whose only clock is `offFromMs` is a session, and v1.192.0 skips it as malformed). The restore clamps `offFromMs` to the restart, keeps `offKnee` only with its clock, and restores the rest under the same two rules as `quietSinceMs` (an outage of at most 10 minutes, and coherent: begun after the session's first crossing and less than 20 minutes before the last reading). Output is sorted by `SEVERITY_ORDER` (critical=0, warning=1, info=2) then category.

#### 2.3 System data-gap / unplanned-outage EVENTS (`outageAlerts()`)

The recorder persists telemetry blackouts (host power loss / add-on stop / MQTT stall) into a gaps sidecar. `outageAlerts(gaps, now, opts)` turns each recent gap into a WARNING push (ISA medium, or **low** when the gap matched a graceful clean-shutdown marker — a deploy). It is an EVENT, not a condition:

- Stable id `outageAlertId(startMs, durationMs)` = `system-outage-<startMs>[-<tier>]`, where `outageDurationTier` is 0 (<15 min), 1 (≥15 min), 2 (≥1 h), 3 (≥6 h). Crossing a tier changes the id so an in-place-extended blackout re-notifies with its true magnitude.
- `isOutageEventFamily()` (id starts `system-outage-`) → **never** sends a "Resolved:" (`shouldSendResolve` returns false) and is NOT firstRun-boot-seeded (`bootSeedNotified`), so a restart-spanning outage fires on the boot that follows it.
- A **critical** is never firstRun-boot-seeded without a notify-state record either (`bootSeedNotified`, v1.187.0 log review): a critical held silent before a restart (a `vdiff-crit` inside its end-of-charge or charging grace across an auto-update) had no record, was seeded "already notified", and was spoken but never pushed when the grace lapsed. A critical that was pushed keeps its record and stays deduped; one that was not pushes once when it annunciates (a duplicate critical push is the safe direction).
- Every time in the outage and gap texts and in their `Started` / `Detected` / `Ended` facts is written on the site clock (`fmtClock`: `SITE_TIMEZONE`, else the container's `TZ`, else `America/Phoenix`; v1.191.0), never the host's zone.
- `resolveOutageAlertOptions(env)` (NaN-safe via `envNum`): `SYSTEM_OUTAGE_ALERT_ENABLED` (default true), `SYSTEM_OUTAGE_RECENT_WINDOW_H` (24), `SYSTEM_OUTAGE_MIN_MINUTES` (15), `SYSTEM_OUTAGE_RESTART_MIN_MINUTES` (5 — lower floor for restart-spanning gaps).
- `outageTracking()` / `systemOutageFields()` feed HA `system_outage_*` sensors, splitting count into `powerOutageCount` (host down) vs `gracefulRestartCount` (deploys) vs `telemetryGapCount` (cloud stall) so a deploy doesn't poison the power-loss trend.
- **Per-device gaps (v1.155.0).** A ledger record carrying `sn` is ONE device silent past the per-device threshold while the rest of the fleet kept writing. It renders as its own alert: title `Device telemetry gap — no data for N min`, `device` = the store's display name (else the SN, so the push title reads `… — Core 2`), and a detail that names the device, says the other home devices kept reporting, and says the gap is measured to detection (the device may still be dark). Its id is `deviceGapAlertId(sn, alertStartMs ?? startMs, durationMs)` = `system-outage-device-<SN>-<alertStartMs ?? startMs>[-<tier>]`, in practice always `-3` (a record is filed only once the device has been dark for more than 6 h, `PER_DEVICE_GAP_THRESHOLD_MS`; `alertStartMs`: the paragraph below): the prefix keeps the outage EVENT lifecycle above, the SN keeps apart devices written in the same batch (and the fleet gap sharing their startMs), `familyOf` rolls them up as `system-outage-device`, and `isEvidenceExemptFamily` exempts them because the id names the dark device. Outage alerts sort by gap start. Per-device records are EXCLUDED from `outageTracking` and every `system_outage_*` field and counted apart by `deviceGapCount()` → `system_device_gap_count_24h` (HA **Device Telemetry Gaps 24h**). `/api/telemetry-gaps` serves `telemetryGapLedgerSummary()` beside the raw ledger: `count` (every record), `fleet_gap_count`, `longest_gap_min` (fleet records only), `device_gap_count`, `longest_device_gap_min`.
- **What the text states (v1.188.1).** A per-device record whose start was moved to the start of the device's held span, the newest row of the device left in `samples` (its last fresh reading, or a restated row a scan left there: architecture chapter, sections 4.4 and 4.7), keeps its id on the start it was first filed with (`alertStartMs`): the detail and the `Started` fact give the new start, and the id, the push and digest dedupe key, does not change, so nothing is pushed again while the alert is listed. A restore of the held span returns the record to that start, under the same id; a record filed at the span's start after the move keeps that start, and the next boot extends it instead of filing a second record (its seed, the restored span's last row, lies inside the record's window, or inside the restored span from its start when a replay ran on past the record's end). A Core whose replayed body is still being written is held from the span's start once the scan has moved part of it, so its record is filed 6 h after that start, once, while the replay goes on, also when it wrote between the scan's plan and its move or first after a restart's boot scan (architecture chapter, section 4.7). Where the scan runs, a device still dark at a boot is filed only once the first scan has finished, so the first push states the start the scan re-dates to; a device that comes back while that scan runs is judged when it has finished, from the clock its first write ended, and a record filed for it ends at that write; and two records of one darkness that a move joins are merged into one under the open record's id. A record whose alert has aged out of the 24 h window and whose device is still dark at a later restart is extended with a new detection time, and its alert, the same id, is delivered again: once a day at most, as before v1.188.1. With several per-device records overlapping in time the detail says how many home devices were dark at the same time (`devicesDarkAlongside`: the most distinct devices whose records cover one instant of this record's window, a window ending as another begins, or beginning as another ends, not counted), not that one device went dark. Counting every record that overlaps the window, two devices dark at either end of a long record, never together, made three. An in-process FLEET gap whose record carries `held` (the evaluations through the silence, none more than 3 min apart and the last that close to its end, found no recordable home reading, and the freshness gate held the devices named: architecture chapter, section 4.7) reads `No fresh home-device readings reached the recorder for N min (…): the add-on kept checking the fleet, but every home device it had a reading for was held — …` and names each device, as a cloud shadow (`the EcoFlow cloud replayed the last payload of …`), as sending no new readings, or, for a device whose rows were written and then moved by the held-sample scan (`replayed`), as `<device> only restated its last readings, which the hourly check moved out of the history as held samples` (`heldGapPhrase`), with the fact `Type: in-process (held readings)`; with a replayed device the sentence ends `so no fresh reading was recorded (only fresh readings are kept)`, not `so nothing was recorded`. When those evaluations also read a home device with fresh content and nothing measurable, never held in the silence (the record's `unmeasured`), it reads `No home-device reading could be recorded for N min (…): the add-on kept checking the fleet, but no home device it had a reading for gave one to record — …; <device> reported nothing measurable`. Without a held set it keeps the MQTT/broker-stall text.
- **Held devices (v1.188.1).** A device the EcoFlow cloud lists offline is filed as a per-device gap too, once it has been silent for more than 6 h of time in which another home device wrote: the recorder no longer restates its held reading as new rows, which had reset its clock (architecture chapter, sections 4.3 and 4.7). Time in which every home device was silent is the fleet gap's and counts toward no device, so a fleet-wide outage files the fleet `Telemetry gap` alone, however the devices come back; so does a fleet-wide hold in which the cloud replays the Cores' cached bodies: the content-clock gate stops writing a Core five minutes after its readings stop changing, and replayed bodies written anyway (before v1.188.1) count once the scan has found them held (their restatements are not home inserts). After a cloud outage that leaves the Cores held while the panel reports again, each Core is filed 6 h after the panel's first fresh reading: one `Device telemetry gap` WARNING per Core, retrospective and never audible, beside the `offline-<SN>` alerts already standing. The offline, stale and blind alarms and the SoC ladder read the live store and are unchanged.

### 3. The four learned-alert families (`analytics.ts`)

Learned alerts carry `source: 'learned'` (→ ISA Medium at warning severity). Robust statistics use `median` + `mad` (median absolute deviation) and a MAD-floored modified z (`robustZ(v, med, mad, floor, floorZ)`). Global gates: `Z_INFO = 3.5`, `Z_WARN = 5`.

#### 3.1 Peer-comparison — `computeLearnedAlerts(devices)`

**WHAT.** For each online DPU with ≥3 packs, compares each pack against its sibling packs on four metrics, flagging the outlier. Naturally cancels positional bias.

`PEER_METRICS` (getters return DISPLAY units):

| key | label | category | floor | source field |
|-----|-------|----------|-------|--------------|
| `temp` | temperature | Thermal | 9 °F | `maxCellTemp ?? temp` (→°F) |
| `voldiff` | cell-voltage spread | Battery | 10 mV | `maxVolDiffMv` |
| `soh` | state of health | Battery | 2 % | `actSoh ?? soh` |
| `soc` | state of charge | Battery | 8 % | `soc` |

**CALCULATION.** Per metric: collect finite sibling values → `med`, `m = mad`. For each pack, `absDev = |v − med|`; skip if `absDev < floor`. Compute `z = robustZ(v, med, m, floor, Z_INFO)` (a bare floor-cross with zero sibling scatter scores exactly `Z_INFO`, not infinity); skip if `z < Z_INFO`. **Hysteresis** (`bumpPeerHit(key)` keyed `metric-sn-pack-packSn`; since v1.173.0 a different pack in the slot re-earns its cycles): require ≥ `PEER_HIT_EMIT_MIN` = 3 consecutive eval cycles before emitting; `prunePeerHitCounts(seen)` resets any key that lapsed a cycle. Severity: `z ≥ Z_WARN && warnEligible ? 'warning' : 'info'`, where thermal outliers are `warnEligible` only on the HOT side (a cold pack is benign). **v1.187.1** — the cell-voltage spread (`voldiff`) is one-sided too: a spread LOWER than the sibling median is the healthy direction (a better-balanced pack, or the first pack to report after the knee relaxes, compared with siblings' staler knee readings), so it is never `warnEligible`, and it is emitted at info with `annunciate: false` and `muteReason` `PEER_SPREAD_LOW_MUTE_REASON` and a detail that says it is not a fault — on screen only: not pushed, not spoken, not counted toward the condition, and (`autoTuneCounts`) not fed to the auto-tune rollups. The high side, and SoC and SoH in both directions, keep the rule above; `vdiff-warn` / `vdiff-crit` judge every pack against fixed limits whatever its siblings read.

**OUTPUT id** `peer-<key>-<SN>-<pk>` with facts: this pack, sibling median, deviation, peer z-score, flag thresholds.

**A cell-spread warning is pushed, not announced (`voldiff` only, v1.187.21).** A `voldiff` outlier at **warning** carries `audible: false` at any SoC and any spread, and its detail says so ("Cell-spread warnings are pushed, not announced; a cell imbalance at the critical line is announced."): card and push unchanged (`annunciate` is not touched), excluded from `conditionFromAlerts` and dropped by the broadcast tick (`speakableAlerts`, the one array that feeds both the level and the spoken message; `pickPrimaryAlert` also refuses it). It reports the same physical signal as the pack's own `vdiff-warn`, push-only since v1.187.12; the pack's `vdiff-crit`, at its fixed lines, is the audible signal for a cell spread. Info outliers and the low side (above) are unchanged, and so are the `temp`, `soh` and `soc` outliers, whose warnings still raise and voice the condition. The push gate (`risingEdgePushes`) reads `annunciate` only, never `audible`. On 2026-10-12 at 18:31:59 the outlier was the only speakable alert and spoke a yellow: Core 2 pack 4 on an evening discharge at 63-65% SoC, raised at 17 mV against a sibling median of 4 mV and a warning from 20 mV (z 5.6), voiced once its 10-minute speak hold ran out; the same pack's `vdiff-warn` rose at 18:36:59, off the speakers. *History:* from v1.187.0 the audible was removed only at the top of charge — `topOfChargeQuietSpread` on the outlier pack's own SoC (`pk.soc ?? projection.soc`) ≥ `VOL_DIFF_PLATEAU_QUIET_SOC_PCT` with its spread below the critical line, after a 2026-09-29 knee in which the first pack to arrive (a ~14 mV deviation) spoke four yellows and an all-clear — and, at the critical line, while the pack's `vdiff-crit` was held by a bounded mute (`alertMonitor.quietPeerSpreadUnderHeldCritical`). With the warning never audible both were redundant, and v1.187.21 removed them.

#### 3.2 Self-baseline — `computeBaselineAlerts(devices, recorder)`

**WHAT.** Each sensor learns its OWN normal range from history, bucketed by hour-of-day (±1 h window) so daily cycles don't false-alarm. Catches "unusual for itself" deviations peer/threshold both miss. Cached ~5 min (`BASELINE_TTL_MS`).

**Targets** (`buildBaselineTargets`): per DPU — `mppt_hv_temp`/`mppt_lv_temp` (floor 9 °F), `pack{N}_temp` (9 °F), `pack{N}_board` (11 °F); per SHP2 — `pair{ch}_w` for paired circuits and `ch{N}_w` for the rest (floor 500 W, `sustained: true`).

**CALCULATION.** Pull `BASELINE_HISTORY_MS` (14 d) of history; need ≥ `BASELINE_MIN_SAMPLES` (8) samples and ≥ `BASELINE_MIN_SPAN_MS` (2 d) span. Bucket samples within ±1 hour of the current hour-of-day (again ≥8). `med`, `m = mad`, `absDev = |live − med|`; skip if `< floor`. For `sustained` load circuits: require the excursion to PERSIST — of the recent `BASELINE_SUSTAINED_MS` (30 min) real-time samples (≥ `BASELINE_SUSTAINED_MIN_RECENT`=3), ≥ `BASELINE_SUSTAINED_FRAC` (0.6) must sit on the same side past the floor, else skip (rejects AC-compressor cycling). `z = robustZ(live, med, m, floor, Z_INFO)`; skip `< Z_INFO`. **Severity:** `sustained` targets are capped at INFO (a bimodal on/off circuit scores huge z every cycle; the dedicated `circuit-overload-<ch>` absolute alert covers real faults); other targets use `z ≥ Z_WARN ? 'warning' : 'info'`.

**OUTPUT id** `baseline-<metric>-<SN>` (e.g. `baseline-pair6_w-<SN>`, `baseline-pack3_temp-<SN>`), title "… unusual for the hour", facts: current, typical-this-hour, deviation, baseline window (days/samples), z-score.

**Regime-shift absorption (v1.42.0).** The baseline is a rolling 14-day hour-of-day median with no stored model, so a persistent behavior change (for example two AC zones exchanging duty roles) is fully absorbed once the new pattern becomes the window majority (≈ 7 days). Until then the deviation is real but is a *new normal*, not an anomaly: `regimeShiftDays` (pure, exported) counts trailing consecutive days whose daily bucket-median deviates in the same direction past the floor, and at ≥ `REGIME_SHIFT_MIN_DAYS` (5) the alert states the situation ("persisted N consecutive days — a new normal pattern the rolling baseline is absorbing, ~M day(s) to full absorption") and sets `annunciate:false` until absorption completes. A trailing day that reverses direction, or deviates under the floor, breaks the streak and restores normal annunciation.

**MPPT targets are load-coupled (v1.187.0).** An MPPT's temperature is a step function of its Core's operating state — near 90 °F idle (|in| + |out| < 30 W), near 120 °F at 300 W and above regardless of how much more — so a same-hour comparison is meaningful only at comparable load. The `mppt_hv_temp` / `mppt_lv_temp` targets carry `loadCoupled` and the live `|totalInWatts| + |totalOutWatts|`, and a past-floor deviation is classified by `mpptBaselineVerdict`:

- **`cooler`** (below typical) — never a hazard. Info, `annunciate:false`, detail and `muteReason` say why.
- **`load-explained`** (above typical, within the load's reach) — all of: the hour's typical load is below the loaded plateau `MPPT_LOAD_PLATEAU_W` (300 W); the Core stepped up to ≥ typical + `MPPT_LOAD_EXPLAINS_MIN_W` (300 W) — now (the live reading) or in a bucket ending at most `MPPT_LOAD_RECENT_MS` (6 h) ago (`loadAgoMs`); and the reading is at or below `mpptLoadCeiling`. Info, `annunciate:false`, with the load figures, the loaded reference and the ceiling in the detail and facts.
- **`anomalous`** (above typical otherwise) — the normal `z ≥ Z_WARN` rule and normal annunciation. Missing load evidence (no history, a null reading, a failed read), a typical already on the plateau, no load step within the lookback, and any reading above the ceiling land here.

**The ceiling.** `mpptLoadCeiling = typical + max(0, loadedRef − typical) · e^(−loadAgoMs / MPPT_COOL_TAU_MS) + floor`: the MPPT's own loaded reference plus the floor while the load runs, decaying toward the hour's typical plus the floor with the heatsink's cool-down (`MPPT_COOL_TAU_MS`, 2 h — measured τ ≈ 1.5-2 h: 120 °F falls to ~105 °F one hour after the load stops and ~97 °F after two); at the 3 τ lookback less than 5 % of the span remains. `loadedRef` is the upper quartile of the MPPT's 14-day buckets **settled** under load — the bucket and the `MPPT_LOADED_SETTLE_BUCKETS` − 1 (2) before it all at ≥ `MPPT_LOAD_PLATEAU_W`, so a short load's heat-up does not drag it down — or `MPPT_LOADED_REF_FALLBACK_F` (122 °F, the house Cores' measured settled upper quartile of 121-123 °F) when fewer than `BASELINE_MIN_SAMPLES` such buckets exist. A reference at or below the typical leaves nothing above the floor to explain, so a temperature typical already on the plateau (possible because the typical is a median over raw change-detected samples, which over-weights a fluctuating loaded MPPT) cannot quiet a hot reading. Without the ceiling, a failed MPPT cooler at 62 °C (144 °F) during an outage-night charge on an idle-typical hour would have been on-screen only; with it that reading warns (house-Core ceilings under load: 130-132 °F). Replayed over 14 days of raw history at 5-minute steps on five Cores, the v1.186.5 rule gave 52 warning episodes and this one none; the median of all loaded buckets as the reference would have left 18 (a Core cycling short 600 W loads reads 101 °F "loaded" against 118 °F settled), the settled median 7.

The typical load, the load step and the loaded references come from `coreActivityContext`: one bucketed (600 s) `queryMulti` of `total_in`, `total_out`, `mppt_hv_temp` and `mppt_lv_temp` over the 14-day window, read only for a hot MPPT excursion and at most once per Core per pass; the typical is the median over the same ±1 h window and needs `BASELINE_MIN_SAMPLES` buckets. Both quiet verdicts stay on-screen but are not pushed, spoken, counted toward the broadcast condition, or fed to the auto-tune rollups (`autoTuneCounts`). The absolute `MPPT_TEMP` band is unchanged. Pack cell and BMS-board targets are **not** load-gated: a pack warming while electrically idle is the internal-fault signature their baseline exists to catch.

#### 3.3 Degradation & runtime forecast — `computeForecastAlerts(devices, recorder, forecast?)`

**WHAT.** Regression-based projections. Cached ~10 min (`FORECAST_TTL_MS`), keyed also on the depletion gate boolean.

- **`forecast-runtime-<SN>`** (SHP2) — linear regression of `backup_pct` over the trailing `RUNTIME_TRAIL_MS` (3 h). Fires only when slope `pctPerHour < -0.05`, `cur > reserve`, AND the diurnal day-ahead forecast ALSO confirms depletion (`diurnalConfirmsDepletion` = `forecast.minProjectedSoc < forecast.reserveSoc`). The displayed time-to-reserve is **bounded** by the diurnal forecast's own first reserve-crossing hour (the flat trailing extrapolation ignores dawn recovery and can read ~4× the authoritative runway). Severity: `<6 h` warning, `≤18 h` info; grid-backstopping downgrades warning→info. Facts include decline rate, implied draw, R², reserve floor, ETA. **v1.181.0:** the grid downgrade is applied by the alert monitor on the main thread (`applyRuntimeGrid`, with the live resolver), not in the analytics worker that computes the alert: the worker never refreshes the HA grid entity, has no persisted-reading source, and caches the alert for `FORECAST_TTL_MS` (10 min).
- **`forecast-soh-<SN>-<pk>`** (info, Battery) — SoH decline → projected months to 85%. Uses its OWN tighter gates: `SOH_FORECAST_HISTORY_MS` (120 d), `SOH_DEGRADE_MIN_SPAN_MS` (45 d), `SOH_DEGRADE_MIN_R2` (0.5), plus `sohStepDominated`/`sohSignalBelowFloor` guards and a `MAX_SOH_FADE_PCT_PER_YEAR` (10%/yr) ceiling — so it fires only on an abnormal ~6–10 %/yr decline, never on normal 2–3 %/yr aging (which would be alarm fatigue and is backstopped by the SoH threshold alarm).
- **`forecast-imbalance-<SN>-<pk>`** (warning, Battery) — cell-spread rising → projected weeks to 50 mV. Shared gates: `DEGRADE_MIN_SPAN_MS` (5 d), `DEGRADE_MIN_R2` (0.25); fires when `mvPerWeek > 0.5` and current spread < 50 mV and `0 < weeksTo50 < 52`.

#### 3.4 Solar/load day-ahead — `forecastDayAlerts(df, grid?)`

**WHAT.** Narrative alerts from the learned solar-response `DayForecast`. Also does **counterfactual driver analysis** — decomposing a shortfall into "cloud cover" vs "everything else (shading/soiling/model error)".

- **`forecast-soc-dip`** (warning; info when grid backstopping, SHP2) — `minProjectedSoc < reserveSoc`. Discriminates severity by *hours-below-reserve* (depth alone is degenerate on a grid-tied home that pins at the floor). `why` text is chosen by average cloud cover (>50% / >30% / else). Facts: projected low SoC, reserve, hours below reserve, expected-at, solar next 24 h, clear-sky ceiling, avg cloud.
- **`forecast-low-solar`** (info, Solar) — `forecastPvWhNext24 < 0.6 × typicalBiasAdjusted`, where `typicalBiasAdjusted = typicalPvWhPerDay × pvBiasFactor` (puts both sides on the same bias basis). `why` attributes the gap to cloud (>60% / >40% / else) vs equipment.
- **`soiling-pv`** (info; warning if `dropPct ≥ 22`, Solar) — clear-sky output ≥ 12% below the clean-panel baseline, with `cleanDays ≥ 6` and `recentCovered !== false`. `audible: false` at every severity (v1.187.1): a maintenance estimate that moves over weeks keeps its card and push but never raises or voices the broadcast condition (§10, 2.1); `conditionFromAlerts` also excludes the id.
